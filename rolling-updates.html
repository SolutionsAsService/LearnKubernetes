Rolling updates

Change the image and Kubernetes replaces pods a few at a time. Two numbers set how bold it is: step through it.

Step through an update

Turn on JavaScript to step through. The YAML below sets the two numbers.

Step through the update.

Dark blue is v2, light is v1, dashed is starting. A simplified model: new pods are ready the next step, and real readiness checks take time.

The two numbers

spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1          # extra pods allowed above replicas during the update
      maxUnavailable: 1    # pods allowed to be unavailable during the update
  • maxSurge: how many pods above replicas may exist while the update runs. More surge is faster and needs spare capacity.
  • maxUnavailable: how many pods may be missing from the serving count. Zero means capacity never drops.
  • They cannot both be zero. If you set neither, both default to 25%, and percentages round surge up and unavailable down (with 3 replicas that is 1 and 0).
kubectl set image deployment/simple-app simple-app-container=nginx:1.27   # the Deployment from the Deploy lesson
kubectl rollout status deployment/simple-app
kubectl rollout undo deployment/simple-app    # back to the previous version
Common mistake. No readiness probe. Without one, Kubernetes counts a new pod as ready the moment its container starts, and a rollout can finish while the app is still booting.
